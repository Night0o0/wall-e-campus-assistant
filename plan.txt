REVISED WHOLE-APPLICATION PLAN WITH MOBILE DESIGN PRESERVATION
================================================================

Scope: backend, React web application, and the complete Flutter mobile
application for every role.


MANDATORY MOBILE DESIGN RULE
============================

The current Flutter design must be preserved throughout implementation.

Existing mobile screens must retain:

- Layout and information hierarchy
- Colors, gradients, backgrounds, borders, and shadows
- Typography, font sizes, weights, and line heights
- Spacing, padding, card sizes, and corner radii
- Icons, buttons, fields, badges, and navigation
- Animations, transitions, scrolling, and responsive behavior
- Loading, empty, success, and error-state styling
- Student, admin, super-admin, and robot visual identities

Functional fixes must be added without redesigning existing screens.

New screens--registration, OTP, password reset, pending approval, editors,
and exports--must reuse the current theme, widgets, navigation patterns, and
visual language. A design change is allowed only when necessary for missing
functionality and must still look like part of the existing application.


PHASE 0 - PRESERVE THE SOURCE AND VISUAL BASELINE
=================================================

1. Review modified and untracked files before committing anything.
2. Check for secrets, generated files, and local build artifacts.
3. Create a safe branch or recoverable backup point.
4. Commit verified work in logical groups.
5. Compile the current Flutter application before functional changes.
6. Capture reference screenshots for every existing mobile screen, role, and
   important state:
   - Normal
   - Loading
   - Empty
   - Error
   - Dialog/modal
   - Small and large mobile sizes
7. Record theme values and reusable widgets.
8. Add targeted Flutter golden-test infrastructure only for this representative
   subset:
   - Login
   - One student-shell screen
   - One admin-shell screen
   - One super-admin-shell screen
   - The robot QR-display screen
9. Use the complete screenshot baseline for manual visual comparison on every
   other existing screen and state. Do not expand golden coverage during this
   remediation unless a screen proves too risky to verify reliably by manual
   comparison.

Success condition: the current design has a reproducible visual baseline that
later work can be compared against.

PHASE 2 - CORRECT BACKEND BEHAVIOR
==================================

2.1 Course authorization - D-10
-------------------------------

Create separate authorization policies:

- canManageCourse
- canExportCourse

Rules:

- Super admins may manage any course in their organization.
- Instructors may export courses they created or actively teach.
- Cross-organization access remains forbidden.
- Instructor course-management policy must match the documented product rules.

Add authorization and tenant-isolation tests.


2.2 Session course data - D-1 and D-3
--------------------------------------

Include course: courseSummary in:

- Session detail
- Organization session list
- Instructor session list

Make the property required-but-nullable:

    course: CourseSummary | null

Linked sessions must include a course; ad-hoc sessions must explicitly return
null.


2.3 Instructor courses - D-4 and D-5
-------------------------------------

Make /courses/my return courses that the instructor:

- Created, or
- Has an active teaching assignment for

Use /courses/my for instructors and /courses for super admins.

Return reliable export authorization so clients never show actions that will
predictably return 403.


2.4 Materials - D-6 and D-7
----------------------------

- Derive publisher scope from the authenticated actor.
- Instructors see and modify only their own materials.
- Super admins see organization-wide materials.
- Add Active, Withdrawn, and All filters.
- Allow authorized reactivation of withdrawn material.


2.5 Session pagination - D-2
-----------------------------

Add validated pagination and metadata to session queries.

Update backend, web, and Flutter consumers together so neither client
temporarily breaks from a response-shape change.

PHASE 6 - MOBILE VISUAL VERIFICATION
====================================

After each mobile feature:

1. Compare the updated screen against its reference screenshot.
2. Run golden tests when the screen is in the targeted golden subset.
3. Perform a documented manual screenshot comparison for every screen outside
   that subset.
4. Test common mobile dimensions.
5. Verify text scaling and overflow.
6. Verify keyboard appearance and field scrolling.
7. Verify dialogs fit smaller screens.
8. Verify dark background, gradients, spacing, and colors remain unchanged.
9. Verify navigation and animations behave as before.
10. Inspect every role independently.

Any unintended visual difference is treated as a regression, even when
functionality works.

New screens must be reviewed for consistency with neighboring existing
screens.


PHASE 7 - DEPLOYMENT SECURITY
=============================

7.1 Migrations
--------------

Follow docs/MIGRATION_RUNBOOK.md as the authoritative procedure. Do not replace
it with an improvised migration sequence.

1. Back up the database.
2. Inspect the live _prisma_migrations ledger read-only.
3. Compare every migration to the live schema read-only.
4. Produce a written classification for every migration: fully reflected,
   partially reflected, or genuinely missing.
5. Prepare the exact proposed prisma migrate resolve and prisma migrate deploy
   commands, together with their expected effects and rollback procedure.
6. Rehearse the complete proposal against staging or a safe database copy.
7. EXPLICIT APPROVAL GATE: the project owner or designated database owner must
   approve the written classification and the exact commands before any
   migration ledger or schema write. Until that approval is recorded, do not
   run migrate resolve, migrate deploy, or manual write SQL against the live
   database.
8. After approval, mark only migrations whose complete effects are already
   present as applied.
9. Apply only genuinely missing migrations.
10. Run migration status, schema verification, and application smoke tests.


7.2 Mail
--------

- Configure SMTP.
- Set MAIL_PROVIDER=smtp.
- Test OTP and password-reset delivery.
- Ensure production logs do not contain codes.


7.3 Device secret
-----------------

- Configure an independent strong DEVICE_JWT_SECRET.
- Store it in the deployment secret manager.
- Document rotation and device revocation.


7.4 Staff-only QR
-----------------

After web, mobile, and robot QR flows are verified, enable:

    QR_ENDPOINT_STAFF_ONLY=true

Verify:

- Students receive 403
- Staff QR works
- Mobile staff QR works
- Device QR works
- Attendance scanning still works

FINAL ACCEPTANCE CRITERIA
=========================

The work is accepted only when:

- All reported functional defects are fixed.
- Backend, web, and Flutter functionality agree.
- Mobile works for students, instructors, super admins, and robots.
- Existing mobile screens preserve their current design and details.
- New screens match the existing mobile visual system.
- The targeted golden tests and the documented manual screenshot comparisons
  show no unintended visual regressions.
- Flutter compiles and passes tests.
- Mobile works on supported screen sizes.
- Migration history is safely reconciled.
- SMTP and device secrets are configured.
- Students cannot generate staff QR tokens.
- Full role-based end-to-end tests pass.

INDICATIVE EFFORT AND BUDGET
============================

For one developer, retain the complete Phase 5 mobile scope and plan for
approximately 5-7 weeks:

- Source protection, baseline, and targeted visual-test infrastructure:
  3-5 working days
- Backend truth, authorization, contracts, and pagination: 5-7 working days
- Web-console corrections: 4-6 working days
- Student mobile onboarding and recovery: 6-8 working days
- Staff and super-admin mobile parity, devices, and exports: 8-12 working days
- Visual comparison, integration testing, deployment gates, and documentation:
  5-8 working days

These ranges may overlap, but the release must not be compressed back to the
previous 2-3 week estimate without explicitly cutting Phase 5 scope and
updating the acceptance criteria to name what was deferred.
