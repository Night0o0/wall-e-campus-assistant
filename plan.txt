10. Confirm creation of all academic tables, indexes, constraints and enums.

Migration replay pre-flight

Migration 11 (20260826123000_leornian_academic_core) rewrites the UserRole enum
- only 2 of 5 value names survive - and adds 15 tables and 4 enums. Prisma does
not roll back across migrations, so a failure part-way through leaves a partial
schema AND a partial ledger.

Therefore, before the real rebuild:

- Replay all 13 migrations from empty against a scratch/disposable database and
  confirm 13 applied, 0 pending.
- Only then run the rebuild against the approved host.

Recovery, if the real replay fails part-way: re-run
backend/scripts/rebuild-database.mjs and then migrate deploy again. This is safe
and repeatable because the script re-verifies emptiness at the moment of use and
refuses on any populated table. Do not hand-patch a partial ledger.

Note on the scope of the rebuild

The rebuild drops and recreates the public schema only. The auth, storage,
realtime, graphql, extensions and vault schemas are never referenced and are
left exactly as they are. This has a direct consequence for Phase 2: see
"Supabase identities survive the rebuild".

PHASE 2 - CREATE A SAFE SUPABASE-AWARE SEED PROCESS

Because authentication will go directly through Supabase, seed accounts must exist in both Supabase Auth and the application database.

Supabase identities survive the rebuild

Dropping the public schema does NOT clear auth.users - identities live in the
auth schema, which the rebuild never touches. So rebuilding the database does
not give a clean slate for identities, and a second seed run will hit "user
already exists" for every account.

Rebuilding first is therefore NOT sufficient to make seeding repeatable. The
seed must be explicitly idempotent on the identity side:

- Key each seed account on its email address.
- If the Supabase identity already exists, adopt it and reuse its user ID
  rather than failing or creating a duplicate.
- Then create or update the matching Prisma User with that authUserId.

Actions

1. Update the seed so every login account is created through the Supabase Admin API.
2. For each account:
   - Create the Supabase identity, or adopt the existing one for that email.
   - Receive its Supabase user ID.
   - Create the Prisma User record.
   - Store the Supabase ID in User.authUserId.
   - Do not create a local password hash.
3. Seed accounts for:
   - One SYSTEM_OWNER
   - Two UNIVERSITY_ADMIN accounts in different universities
   - At least one DEPARTMENT_ADMIN
   - At least two instructors
   - One pending student
   - One approved student
   - One rejected or disabled student
   - A second-university student for tenant-isolation testing
4. Seed academic data:
   - Organizations
   - Departments
   - Academic terms
   - Cohorts
   - Courses and offerings
   - Teaching assignments
   - Enrollments
   - Timetables
   - Materials
   - Assignments
   - Attendance sessions
   - Notifications
5. Make the seed fail safely:
   - Development/test environments only
   - Exact remote-host approval required
   - Never allowed in production
   - Clear warning that it creates demo accounts
   - Clean up the Supabase identity if the Prisma user creation fails, but only
     when this run created it - never delete an identity it adopted
   - Avoid leaving partial identity/application records
6. Switch AUTH_PROVIDER to supabase as part of this phase, not after it.
   Seeding Supabase-only accounts (no passwordHash) while the backend still
   defaults to AUTH_PROVIDER=legacy leaves no account able to log in. The seed
   and the provider switch are one unit of work.

Verification

- Every seeded identity exists in auth.users.
- Every application user has the correct authUserId.
- No user contains a local passwordHash.
- Each seeded account can authenticate with Supabase.
- Roles and organization IDs are correct.
- Running the seed twice in a row succeeds and produces the same result.

Completion criteria

A clean database can be transformed into a fully testable development environment with one documented seed command, repeatably.

PHASE 4 - COMPLETE STUDENT REGISTRATION

Final registration sequence

1. Student enters:
   - University code
   - University ID
   - Full name
   - University email
   - Password and confirmation
2. Client validates the form.
3. Supabase creates only the authentication identity.
4. Supabase sends the confirmation email.
5. The student confirms the email.
6. The confirmation callback restores the Supabase session.
7. The client sends the confirmed access token and registration information to the backend.
8. The backend derives:
   - Email from the verified token
   - authUserId from the verified token
   - Role as STUDENT
   - Initial status as PENDING
   - Verification state as awaiting university approval
9. The backend finds the organization using the supplied organization code.
10. The backend checks that email and university ID are unused.
11. The backend creates the application user and empty student profile.

Cross-device completion

The current web flow depends partly on browser localStorage. That can fail if a student opens the confirmation email on another device.

Fix the design by putting only non-authoritative registration fields in Supabase user metadata or a short-lived registration record. Role and account authority must never come from that metadata.

The backend must always force:
- Role: STUDENT
- Status: PENDING
- Organization resolved from a valid organization code
- Email derived from the verified identity

Failure handling

Handle:
- Unknown university code
- Duplicate university ID
- Duplicate email
- Expired confirmation
- Missing registration information
- Repeated completion request
- Identity created but application registration incomplete

Repeated registration completion should be idempotent and return the already-created account when appropriate.

Completion criteria

Registration succeeds on the same device and across devices, always creates a pending student, and cannot create a staff or owner account.
