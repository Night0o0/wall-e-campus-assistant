Every page in apps/web is responsive and works at every width. "Mobile" above
is not a separate application: it is a REDUCED NAVIGATION MENU, defined per role
in apps/web/src/lib/navigation.ts by the `mobile` flag on each entry.

The distinction matters. A super admin has nine pages, and a phone menu of nine
is a phone menu nobody reads. The ones marked `mobile` are the pages somebody
actually opens while walking across campus; the rest stay reachable by URL and
by every in-page link, they are simply not in the small-screen menu. This is an
editorial decision per role, revisited by editing one array — not a breakpoint,
and not a capability difference.

  ADMIN on a phone        : My Teaching, Sessions, Pending Students, Account
  SUPER ADMIN on a phone  : Dashboard, Sessions, Students & Staff,
                            Pending Students, Robot Devices

THE STUDENT HAS NO WEB CLIENT. This is deliberate, not missing work. A student
who signs in to apps/web is shown an explanation and pointed at the mobile app
rather than a shell that would 403 on every request inside it.

0) ROBOT - 2 PAGES
===============================================================================

THE ROBOT IS A DEVICE ACCOUNT, NOT A TABLET.

  There is no apps/tablet, no kiosk build, and no hardware assumption anywhere
  in the code. /robot is an ordinary route in apps/web. Run it on a wall screen,
  a spare laptop, a phone propped against a lectern — the platform is
  irrelevant and nothing in the client asks what it is running on.

  What makes it a robot is the CREDENTIAL. A device authenticates with a key id
  and secret at POST /api/devices/auth, receives a token signed with
  DEVICE_JWT_SECRET — a different key from any user token — and can reach
  exactly four endpoints. `authenticateDevice` guards them, never
  `authenticate`, so no route below is reachable by a user token and no route
  anywhere else is reachable by a device token.

+---------------------+------------------------------+--------------------------------------------------+
| PAGE                | FUNCTION                     | DATA IT CONTAINS                                 |
+---------------------+------------------------------+--------------------------------------------------+
| 1. QR Display       | Show the attendance code for | Rotating QR, course code + name, session title,  |
|                     | a session a HUMAN opened.    | room, live scan count, refresh countdown.        |
+---------------------+------------------------------+--------------------------------------------------+
| 2. Mapping          | Navigation / campus map.     | NOT STARTED. No backend exists for this. Nothing |
|    ** later **      |                              | in backend/ serves it.                           |
+---------------------+------------------------------+--------------------------------------------------+

PAGE 1 HAS FOUR STATES, all implemented in pages/robot/RobotConsole.tsx:

  PAIRING   Key id + secret, asked for once. The only state that ever asks a
            human for anything.
  IDLE      Paired, nothing open. Where the screen spends most of the day,
            which is why it is designed rather than left blank.
  PICKING   More than one session matches. Shown only when the choice is
            genuinely ambiguous.
  SHOWING   One session, its code, rotating every 25 seconds.

  A SINGLE MATCHING SESSION AUTO-SELECTS. Making somebody tap through a list of
  one, in front of a waiting lecture hall, would be a worse default. The picker
  exists because two sessions can share a room, and an unbound device sees the
  whole university — guessing there would put the wrong course's code on a wall.

TIMING
  A QR token expires 30 seconds after the server signs it (utils/qr.util.ts).
  The client refreshes at 25. The five-second margin covers the round trip and
  the seconds between a student raising their phone and the scan landing.

  The device ACCESS TOKEN lives DEVICE_TOKEN_TTL_MINUTES (default 15). The
  console re-exchanges its stored credential silently on 401 rather than
  dropping to the pairing screen — a robot that asks for its secret every
  quarter of an hour is a robot nobody deploys.

THE ROBOT CANNOT OPEN A SESSION
  No button, no endpoint, no capability. The `session:open` capability was
  deleted outright rather than shipped switched off, because a permanently
  disabled permission is an invitation to enable it. Session.createdById is in
  any case a non-nullable foreign key to User, which a device cannot satisfy.

APIs used:
  POST /api/devices/auth
  GET  /api/devices/me
  GET  /api/devices/me/sessions/active
  GET  /api/devices/me/sessions/:id/qr

WHERE THE CREDENTIAL COMES FROM
  Super Admin page 7, Robot Devices. The secret is shown once at provisioning
  and never again — only bcrypt over it is stored. Lost secret means rotate.


===============================================================================
THE APPROVAL FLOW
===============================================================================

  Student registers -> verifies email -> PENDING -> Admin approves -> ACTIVE

EMAIL VERIFICATION (new, 16 Aug 2026)
    Registration is three requests, and the address is proven BEFORE the
    account exists:

      1. POST /api/auth/verify-email/start    -> a 6-digit code is mailed
      2. POST /api/auth/verify-email/confirm  -> code spent, ticket returned
      3. POST /api/auth/register              -> ticket presented with the account

    Verifying first means an abandoned signup leaves NOTHING behind: no User row
    holding the unique claim on an email address or a university ID that
    somebody else may legitimately need.

    ENFORCEMENT IS BEHIND A FLAG. STUDENT_EMAIL_VERIFICATION_REQUIRED ships
    false, for the same reason QR_ENDPOINT_STAFF_ONLY does: the client that has
    to change is not in this repository. The Flutter app registers with no
    ticket today, and turning this on before it implements the OTP screens would
    stop student registration outright. Turn it on once the app sends
    `verificationTicket`.

WHAT A PENDING STUDENT CAN DO
    Log in.                              /api/auth/login
    Read and fill their own profile.     /api/students/me/profile

WHAT A PENDING STUDENT CANNOT DO
    Timetable, QR scan, attendance history, attendance summary, materials.
    All answer 403 with code "ACCOUNT_PENDING_APPROVAL", which the client
    branches on to show a "waiting for approval" screen.

WHY LOGIN IS NOT BLOCKED
    Deliberate. If PENDING blocked the token, the student could never fill in
    their profile, and staff would be approving a row carrying nothing but a
    name and an email address. Letting them in as far as the profile — and no
    further — is what makes the approval a real decision.

WHO APPROVES
    Any ADMIN in the same university, plus UNIVERSITY_SUPER_ADMIN. Routing every
    registration through one super admin would make that person the bottleneck
    for the whole university at the start of term.

    Approval stamps verifiedAt and verifiedById in the same write as the flag.
    Approving twice is a no-op, so two people working the queue do not collide.

THE STUDENT IS NOW TOLD (new, 16 Aug 2026)
    Approval and rejection each write a Notification IN THE SAME TRANSACTION as
    the decision. Both rows commit or neither does.

    One transaction rather than two writes, because the orderings fail in
    different but equally unacceptable ways: approve-then-notify can leave a
    student admitted and never told, staring at a waiting screen that will never
    change; notify-then-approve can tell them they are in while they are not.

    Neither message names the member of staff who decided. verifiedById records
    that; a student reading "Dr. X rejected you" turns an institutional decision
    into a personal one, and the appeal route is the department.

REJECTION
    Deactivates (isActive = false) rather than deleting. The row is the only
    thing holding the unique claim on that university ID. Login then answers
    "This account has been deactivated".


===============================================================================
PASSWORD RECOVERY
===============================================================================

STUDENTS - self-service, by email
    POST /api/auth/forgot-password  -> code mailed
    POST /api/auth/reset-password   -> code spent, new password set

STAFF - administrator-mediated, by decision
    An ADMIN who forgets their password contacts the UNIVERSITY_SUPER_ADMIN,
    who sets a new one from Students & Staff (PATCH /api/admin/users/:id/password).

    A staff account approves registrations and publishes material to whole
    cohorts, so recovering one is a decision a person makes about another person
    — not something a mailbox can authorise on its own. A staff member who uses
    the forgot-password form receives an email SAYING THIS, rather than a code
    or silence, so the endpoint's answer stays identical for every address.

NO ENUMERATION
    /verify-email/start and /forgot-password answer identically for every
    address and decide privately what to send:

      no account          -> forgot-password sends nothing at all
      account exists      -> verify-email sends "you already have an account"
      staff account       -> forgot-password sends the explanation above
      active student      -> a code

    Exactly one party learns anything, and it is whoever reads the inbox.

THE FOUR LIMITS ON A CODE
    Six digits is one of a million: a good secret or a hopeless one depending
    entirely on the limits around it. They are a SET — relax any one and the
    others stop being sufficient.

      OTP_TTL_MINUTES (10)             guessable given unlimited time; not
                                       given ten minutes
      OTP_MAX_ATTEMPTS (5)             5 tries per code, not 10^6
      OTP_MAX_PER_EMAIL_PER_HOUR (5)   otherwise the attempt ceiling is beaten
                                       by requesting a fresh code every 5 guesses
      OTP_RESEND_COOLDOWN_SECONDS (60) stops the endpoint being a mail cannon

    Plus: issuing a code CONSUMES the previous live one, so a code read over
    somebody's shoulder dies the moment they request a fresh one. The code is
    never stored — only bcrypt over it, so a leaked database yields nothing.

KNOWN LIMITATION, recorded rather than hidden
    Existing access tokens survive a password reset. Tokens are stateless JWTs
    with a 7-day expiry and there is no token-version column to bump. Closing
    that needs a revocation column on User and a check in the auth middleware —
    a deliberate change, not something to smuggle into this one.

READ THIS BEFORE BUILDING THE ACHIEVEMENT PAGE
    Every total is a count of RECORDED attendance, and the API field is called
    `recordedLectures` so it cannot be quietly read as a lecture count.

    A lecture nobody opened a session for leaves NO attendance row at all. It is
    therefore in neither the numerator nor the denominator. The UI must say
    "recorded lectures", never "lectures", or it will state a percentage the
    data does not support.

    `attendanceRate` is null - not 0 - when nothing has been recorded yet. A
    student with no records has not missed anything.

    LATE counts as attended. ABSENT is written only by the absence sweep, never
    by a student.

TWO ERROR STATES THE CLIENT MUST HANDLE
    403 ACCOUNT_PENDING_APPROVAL  -> the waiting screen (screen 8).
    400 from /api/materials/my    -> profile incomplete. The response carries
                                     `profileStatus` and `missingFields`; send
                                     the student to Profile with those fields
                                     highlighted, not to a generic error.

Export rule: an ADMIN can only export a course they are ASSIGNED to - meaning
they instruct an active LectureSchedule for it, or they created the course.
Any other course in their own university returns 403.

Material rule: an ADMIN publishes by picking one of THEIR OWN lectures. The
service copies the academic address (faculty / department / level / semester /
section) off that lecture, which is simultaneously the proof that they teach the
cohort. Naming a cohort directly is refused for an ADMIN - that parameter is the
one through which an instructor could address a year they have nothing to do
with. An ADMIN can only edit material they published themselves.

Multiple years / multiple sections: ONE ROW PER AUDIENCE. The same course taught
to level 2 and level 3 gets two links. A link with section = null covers EVERY
section of its cohort, so an instructor teaching A, B and C from one folder adds
ONE row, not three.

The cohort is NOT editable after creation. Re-addressing a link to a different
year is not an edit, it is a different link, and silently moving one out from
under the students already using it is worse than adding a row.

ANSWERING "WHICH YEAR, WHICH SUBJECT"
    Every drill-down is a filter on an existing endpoint, scoped to their own
    university by the token:

      Second-year mechatronics timetable
        GET /api/schedules?department=Mechatronics&level=2

      Second-year mechatronics subjects
        GET /api/courses?department=Mechatronics&level=2
        (Course has no level of its own - a subject can be taught to several
        years - so `level` resolves through the active LectureSchedule rows.)

      Everyone in a department

      One instructor's lectures
        GET /api/schedules?instructorId=...

WHAT A SUPER ADMIN CANNOT DO
    Create another UNIVERSITY_SUPER_ADMIN, or a SYSTEM_OWNER. The creatable role
    enum is ADMIN and STUDENT only - a super admin creating a super admin is
    escalation with no ceiling. The university-administrator role is granted by
    the platform owner through /api/users and nowhere else.

    Change an existing account's role. There is no role field on the update
    schema; moving an account between roles is a different account.

    Edit a fellow super admin, or the platform owner's account. Those answer
    404, the same as a user from another university.

===============================================================================
THE TENANT RULE - READ BEFORE ADDING ANY ENDPOINT
===============================================================================

organizationId is ALWAYS taken from the authenticated user's token-backed
record, and NEVER from a query string, path or body.

The two platform-owner routes are the exception that proves it:

  GET /api/metrics/overview   aggregates across every university on the
                              platform.
  GET /api/users              reads its organization from a CLIENT-SUPPLIED
                              query parameter.

Both are safe only because requireOwner keeps them to SYSTEM_OWNER, who is
legitimately allowed to browse any tenant. Neither may ever be opened up by
relaxing its guard. The university-scoped equivalents - /api/admin/overview and
/api/admin/users - exist precisely so that nobody is ever tempted to.

The technique, used throughout: the tenant is a required first argument to the
repository method, and it is spread LAST into the where clause, so no filter
derived from a request can displace it. The query schemas do not even declare an
organizationId field, so Zod strips one before it can reach a service.

apps/web/src/api/campus.ts follows the same rule from the other side: no
function in it accepts an organization id, because sending one would be dead
weight at best and a misleading suggestion that it does something at worst.


===============================================================================
OUTSTANDING - DEPLOYMENT STEPS, NOT GAPS
===============================================================================

1. MIGRATIONS ARE WRITTEN BUT NOT APPLIED.

   Ten migrations, all reporting unapplied, including 20260802073548_init. The
   _prisma_migrations table on the Supabase database is EMPTY, which means the
   database was set up by some route other than the migration history.

   Running `prisma migrate deploy` as-is will therefore attempt to replay `init`
   over tables that may already exist. RESOLVE THE HISTORY FIRST — see
   docs/MIGRATION_RUNBOOK.md, which is written to be executed by a human and
   starts with a read-only comparison rather than with `resolve`.

   The two newest migrations:

     20260814090000_course_materials_and_approval_audit
       CourseMaterial + User.verifiedAt / verifiedById. Strictly additive, and
       deliberately does NOT backfill isVerified: every student currently in the
       database reads false, which is correct, because nobody has approved them.

     20260816090000_email_challenges_and_account_notices
       EmailChallenge + two new NotificationType values. Strictly additive. One
       PostgreSQL rule shapes it: ALTER TYPE ... ADD VALUE may run inside a
       transaction on PG 12+, but the value cannot be USED in that same
       transaction — so the file adds the labels and writes no rows.

2. QR_ENDPOINT_STAFF_ONLY IS STILL false.

   /api/sessions/:id/qr remains reachable by any authenticated user, students
   included. A QR token is an ordinary JWT whose payload reads without a secret,
   so a student who scans once legitimately learns the session id and can then
   mint fresh 30-second codes for as long as the session stays open.

   The robot console now exists and runs on /api/devices/*, so the blocker is
   no longer code — it is PROOF. See docs/QR_CUTOVER.md.

3. DEVICE_JWT_SECRET IS NOT SET.

   It is derived from JWT_SECRET with a warning when absent. Still independent
   key material, but set it explicitly before the robot ships so the two can be
   rotated separately. Rotating it invalidates live device tokens; the TTL is
   15 minutes and robots re-authenticate on their own, so the impact is a brief
   reconnect rather than a re-pairing.

4. MAIL_PROVIDER MUST BE CONFIGURED BEFORE PRODUCTION.

   Production REFUSES TO BOOT on MAIL_PROVIDER=log. Student registration and
   password recovery both depend on real delivery, and the logging provider
   would print one-time codes into the server log while telling the caller they
   had been sent. Set SMTP_HOST and MAIL_PROVIDER=smtp.
