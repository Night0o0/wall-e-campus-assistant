  PAGES_AND_GAPS.txt states, in three separate places, that the student client
  is "a Flutter app, OUTSIDE this repository" and that mobile means "a reduced
  navigation menu inside apps/web". Neither is true of the working tree any
  more. apps/mobile/ exists, is untracked in git, is 7,238 lines of Dart, and
  serves ALL FOUR roles - student, admin, super admin and robot - with its own
  screens, not a reduced apps/web menu.

  Everything below is therefore reviewed against the plan's STUDENT page list,
  but the plan itself is out of date on where that client lives.

  The Flutter app was NOT compiled. These are source-reading findings.

10) WHAT IS DEMONSTRABLY SOLID
===============================================================================
Stated plainly, because the defect list above is longer than the praise and
that would give a misleading impression of the codebase.

  THE TENANT RULE HOLDS. organizationId is taken from the token-backed user
  record everywhere and spread LAST into every where clause. The query schemas
  do not declare an organizationId field, so Zod strips one before it reaches a
  service. The two owner-only exceptions (/api/metrics/overview, /api/users)
  are both behind requireOwner. No path was found that violates this.

  THE TWO PRINCIPAL TYPES ARE GENUINELY SEPARATE. Device tokens are signed with
  DEVICE_JWT_SECRET, land on a different request property, and are checked by
  authenticateDevice - which guards device.routes.ts and nothing else. A user
  token cannot reach a device route and a device token cannot reach a user
  route. The client mirrors this with two axios instances (lib/api.ts and
  lib/deviceApi.ts) so a token cannot be sent to the wrong surface by accident.

  THE ROBOT CANNOT OPEN A SESSION. No route, no capability, and
  Session.createdById is a non-nullable FK to User. This is enforced three ways.

  ATTENDANCE COUNTING IS CONSISTENT. The `attendedCount` constant
  (session.repository.ts:47) excludes ABSENT from every session projection, so
  the robot's screen, the admin's list and the attendance log cannot disagree.
  Roll size is reported separately as `roll`. 348 backend tests cover the
  lifecycle, the scan hardening, the summary arithmetic and the absence sweep.

  THE APPROVAL DECISION AND ITS NOTIFICATION COMMIT TOGETHER. One transaction,
  so a student is never admitted-and-not-told or told-and-not-admitted.

  THE OTP LIMITS ARE A COMPLETE SET. TTL, attempt ceiling, per-email hourly
  ceiling, resend cooldown, previous-code consumption, and bcrypt-only storage.
  All are configurable and all are tested.

  BOTH TYPESCRIPT PROJECTS COMPILE CLEAN AND ALL 360 TESTS PASS.

11) DEPLOYMENT BLOCKERS (quoted from the project's own documents;
    NOT independently verified - no database or environment was touched)
===============================================================================

  1. TEN MIGRATIONS ARE WRITTEN AND REPORTED UNAPPLIED, including
     20260802073548_init. PAGES_AND_GAPS.txt records that the
     _prisma_migrations table is empty, meaning the database was built by some
     route other than the migration history. `prisma migrate deploy` would try
     to replay init over existing tables. docs/MIGRATION_RUNBOOK.md is the
     procedure and it correctly starts with a read-only comparison.
     Migrations present on disk: 10 (backend/prisma/migrations/).

  2. QR_ENDPOINT_STAFF_ONLY=false. Verified in code: session.routes.ts:30 -
     the guard array is empty while the flag is off, so GET /api/sessions/:id/qr
     is reachable by ANY authenticated user, students included. A QR token is a
     plain JWT whose payload reads without a secret, so a student who scans once
     learns the session id and can mint fresh codes for as long as the session
     is open. The robot console now exists and runs on /api/devices/*, so the
     blocker is proof, not code. See docs/QR_CUTOVER.md.

  3. DEVICE_JWT_SECRET is unset in .env.example (line 20) and is derived from
     JWT_SECRET with a warning. Set it before the robot ships.

  4. MAIL_PROVIDER=log in .env.example (line 135). Production refuses to boot
     on this value - correctly, since the logging provider would print one-time
     codes into the server log while telling the caller they were sent.

  FLAG STATE (backend/.env.example, verified):
    BILLING_ENABLED=false / VITE_BILLING_ENABLED unset ... off
    QR_ENDPOINT_STAFF_ONLY=false ......................... off
    STUDENT_EMAIL_VERIFICATION_REQUIRED=false ............ off
    DEVICE_ROOM_FILTER_STRICT ............................ off
    SCAN_ALLOW_UNLINKED_SESSIONS ......................... on

  Note on flag 3: STUDENT_EMAIL_VERIFICATION_REQUIRED ships off because "the
  Flutter app registers with no ticket today". That is now understated - the
  Flutter app does not register AT ALL. Turning this flag on would change
  nothing, because nothing calls /auth/register.
